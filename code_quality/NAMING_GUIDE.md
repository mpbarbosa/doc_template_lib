# Naming Guide

Naming is the primary documentation of code. A well-named identifier
communicates intent to every reader — human or LLM — without requiring
surrounding context to interpret it.

## Goal

Establish naming conventions that make every identifier interpretable from its
name alone, so that the purpose of any symbol, file, or test is clear without
reading its body, its callers, or its history.

## What Consistent Naming Means

Consistent naming means every identifier follows conventions that are uniform
across the codebase, rooted in domain vocabulary, and precise enough to be
unambiguous in isolation.

In practice, it means:

1. Every name describes what the symbol *is* or *does*, not how it does it.
2. Names use domain vocabulary — the language of the business problem — rather
   than implementation vocabulary.
3. Functions are verb phrases; classes are specific nouns; booleans are
   predicates; constants name meaning, not value.
4. File names match the primary symbol they contain.
5. Test names describe the scenario and its expected outcome, not the function
   under test.
6. Abbreviations that are not universally known in the domain are not used.

It does **not** mean enforcing a rigid naming system regardless of context.
Layer-appropriate vocabulary matters: domain layer names use business terms;
infrastructure layer names may use technical terms where they are precise and
universally understood.

## Why It Matters

1. A well-named identifier reduces the context an LLM or human reader must
   load to understand a piece of code. A poorly named one forces a body read
   on every encounter.
2. Domain vocabulary in names makes the relationship between code and
   requirements explicit, reducing the translation layer between business
   intent and implementation.
3. Consistent naming conventions allow pattern recognition to generalize: when
   all validators are named `*Validator`, all repositories `*Repository`, a
   reader encountering a new one knows what to expect.
4. Precise names surface design problems. If a name is hard to find, the
   abstraction may be wrong. If a class name requires "and", it has multiple
   responsibilities.
5. AI tools generate names under time and context pressure. Without a
   convention, generated names drift toward generic, implementation-biased
   identifiers that accumulate as technical debt.

## Naming and Code LLMs

Naming directly affects LLM context efficiency and generation quality.

A precise name is a compressed semantic token: `calculateRetryDelay` tells an
LLM what a function does, what its output represents, and where it belongs in
the codebase — without reading the body. A generic name (`process`, `handle`,
`doThing`) forces a body read, consuming context budget.

Consistent naming also enables pattern-based generation. When all repository
classes follow the same `*Repository` convention, an LLM asked to generate a
new one does so correctly from the name alone.

### Why LLMs Benefit

- Precise names eliminate ambiguity in prompt interpretation and code
  generation.
- Convention-consistent names allow an LLM to match the established pattern
  without reading every existing file.
- Domain vocabulary in names keeps generated code anchored to the problem
  rather than the implementation.
- Predicate-form booleans make conditional logic generated by LLMs
  self-documenting.

### Where Weak Naming Hurts LLMs

- Generic names force the LLM to read the body before reasoning about the
  symbol, consuming context on every encounter.
- Inconsistent conventions produce generated code that deviates from the
  project's established patterns.
- Abbreviations the LLM cannot resolve from domain context produce guesses
  that may be plausible but wrong.

## Required Rules

1. No generic unprefixed names: `util`, `helper`, `common`, `manager`,
   `handler`, `processor`, `service` are not acceptable as standalone names.
   Each must carry a qualifying domain noun.
2. Every function name must contain a verb.
3. Every boolean-returning function must be in predicate form: `is*`, `has*`,
   `can*`, `should*`.
4. Abbreviations not universally known in the domain are prohibited in public
   identifiers.
5. Names must use domain vocabulary. Infrastructure terms (`DTO`, `Entity`,
   `Model`, `Mapper`) must not appear in domain layer identifiers.
6. File names must match the primary class, function, or concept they contain.

## Naming by Symbol Type

| Symbol | Convention | Good example | Bad example |
| --- | --- | --- | --- |
| Class | Specific noun | `OrderValidator` | `Validator`, `OrderHelper` |
| Interface / abstract type | Domain noun, no `I` prefix | `PaymentGateway` | `IPaymentGateway`, `PaymentInterface` |
| Function | Verb + specific noun | `calculateRetryDelay` | `process`, `doCalc` |
| Boolean function | Predicate: `is*`, `has*`, `can*` | `isExpired()` | `checkExpiry()`, `expired()` |
| Constant | Semantic meaning, not value | `MAX_RETRY_ATTEMPTS` | `THREE`, `RETRY` |
| Variable | Noun describing what it holds | `pendingOrders` | `data`, `result`, `temp` |
| Test name | Scenario + expected outcome | `returns 404 when order is not found` | `testGetOrder`, `orderTest` |
| File | Primary symbol it contains | `OrderValidator.js` | `validation.js`, `utils.js` |
| Directory | Domain concept or layer | `payments/`, `core/` | `stuff/`, `misc/` |

## Best Practices

### Choosing Precision

1. If two different names seem equally appropriate, neither is precise enough.
   Narrow the scope until only one name fits.
2. Prefer a longer precise name over a shorter ambiguous one. Identifiers are
   not typed — they are read.
3. When naming is hard, reconsider the abstraction. A class that is difficult
   to name often has multiple responsibilities.

### Domain vs. Infrastructure Vocabulary

1. Domain layer names use the language of the business problem.
   `PremiumSubscription`, `OrderFulfillment`, `RefundPolicy` — not
   `SubscriptionRecord`, `OrderData`, `RefundDTO`.
2. Infrastructure layer names may use technical terms where they are precise:
   `PostgresOrderRepository`, `StripePaymentGateway`, `RedisCache`.
3. Never let infrastructure vocabulary cross a layer boundary into domain
   names. `UserEntity` in a domain model couples the domain to the ORM.

### Abbreviations

1. Permit only abbreviations that are universally known in the relevant domain
   or in standard programming vocabulary: `id`, `url`, `http`, `api`, `io`.
2. Acronyms in names follow the same casing as surrounding words:
   `orderId`, not `orderID`; `httpClient`, not `HTTPClient` (unless the
   project's language convention specifies otherwise — pick one and apply it
   uniformly).
3. If a new team member would need to ask what an abbreviation means, expand
   it.

### Collections and Plurals

1. Collection variables use the plural of the item name: `orders`, not
   `orderList`, `orderArray`, `orderCollection`.
2. Functions returning a collection use a plural noun phrase:
   `findExpiredOrders()`, not `getOrderList()`.
3. Functions returning a count use a noun + `Count` suffix:
   `pendingOrderCount()`, not `getTotal()`.

## Review Heuristics

### Rename Test

Can you think of a second name that is equally plausible for this symbol? If
yes, the name is not precise enough. A correct name should be the only name
that fits.

### Cold Read Test

Given only the identifier name, can a reader predict what it does, returns, or
represents without opening the file? Apply this especially to functions, class
names, and test names.

### Domain Test

Would a domain expert — someone who understands the business problem but not
the implementation — recognize and correctly interpret this name? If not, the
name is using implementation vocabulary where domain vocabulary belongs.

### Predicate Test

Does every boolean-returning function read naturally in a conditional
expression? `if (order.isExpired())` reads correctly; `if (order.checkExpiry())`
does not. A failing predicate test is a naming violation, not a style
preference.

### Abbreviation Test

Would a developer joining the team today understand every abbreviation in the
codebase without a glossary? If not, expand the abbreviation.

## Positive Signals

- Code reads like prose: `if (subscription.isExpired()) { cancelSubscription(subscription) }`.
- Class names describe domain concepts; no class is named after what it does
  to data (`Processor`, `Handler`, `Manager` without a subject).
- File names match the primary symbol they contain; no `utils.js` or
  `helpers.ts`.
- Test names describe scenarios and expected outcomes; no `testGetUser` or
  `orderTest`.
- Constants describe meaning; no magic numbers or single-letter constants
  outside of universally accepted conventions (loop counters, math).
- An LLM generating a new module from existing names produces identifiers that
  follow the established pattern without correction.

## Warning Signs

- Classes named with generic agent nouns: `Manager`, `Handler`, `Processor`,
  `Coordinator`, `Controller` with no domain subject.
- Functions named `process`, `handle`, `execute`, `run`, `do`, `perform` with
  no specific subject.
- Boolean functions not in predicate form: `checkUser()`, `validateOrder()`,
  `expired()`.
- Infrastructure vocabulary in domain identifiers: `UserDTO`, `OrderEntity`,
  `ProductModel` in business logic.
- Abbreviations that require team knowledge to decode: `usrMgr`, `cfg`,
  `proc`, `tmp`.
- Files named after their category, not their content: `utils.js`,
  `helpers.ts`, `common.js`, `shared/index.js`.
- Test names that describe the function under test, not the scenario:
  `testCalculateTotal`, `getOrderTest`.
- Collection variables named with a type suffix: `orderList`, `userArray`,
  `itemCollection`.
